**Attribute filter keys are checked against the item type instead of being plain strings.** `JigFilterProperty` took its `key` as `string`, so a typo produced a condition that matched nothing at runtime with no sign anything was wrong. The key is now `Extract<AllKeysOfUnion<TData>, string>`, the same shape `jig-table` already uses for its column keys, and falls back to `string` when the payload type is unknown or the generic is left unspecified. An attribute that is computed rather than read from a property uses `computedKey` instead of `key` and must supply a `selector`. The two are separate fields on purpose: if both kinds shared `key`, its type would widen to `string` and an editor could no longer complete the item's own property names. They are mutually exclusive, so an attribute is identified one way or the other. A `selector` remains available alongside `key` for the case where a known property is read some other way — a nested or normalised value — with the key still naming the attribute. A type-level test pins all of this. `JigFilterProperty` gained a second parameter for the payload, because `jig-filter-bar` holds `JigItem`s whose keys index `item.data`: the selector still receives the item while the key is checked against `JigFilterProperty<Item, Person>`. The new `JigItemsData` exposes that payload type beside the existing `JigItemsValue`, resolving a group to its children's payload. A condition's `attribute` in the emitted configuration stays a `string`, since it must carry a computed attribute's identifier and survive a round trip through a server.
