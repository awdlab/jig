**A list box that ships its own search field, and a filter that picks its own attribute.** `JigListBox` has `filter` and `filterText` inputs but renders no input for the text, so every long list re-implemented one. `jig-filter-list-box` composes that field with the list, debounced and two-way through `searchText`, and `jig-attribute-filter` adds the piece `jig-filter` could not express: a condition whose attribute is chosen per row, so a list of users can be filtered by "email contains @gmail.com and role is Admin". Conditions join by one `all`/`any` match mode — no nesting, no mixing — and the emitted config is data-free and serializable, so `filterLocally="false"` hands it to a server instead. Pass `attributes` to the list box and it grows a filter trigger with an active-condition badge and a row of removable chips, all rendered from the configuration rather than from the filtered result, so they read the same locally and server-side. Attribute values resolve by one rule shared with the new `executeAttributeFilter`: a descriptor's `selector`, else `key` indexed on the item, through `data` for a `JigItem`. Grouped items keep a group whose children survive. `jig-filter` is unchanged apart from newly exporting `defaultOperatorsForType` and `OperatorDef`; `jig-input-field` now hides its clear button while `readonly`, which previously let a click wipe the value a read-only field was showing.
