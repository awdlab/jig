### Roles & Attributes

Neither directive adds roles or ARIA attributes, and neither makes its host
focusable.

### Keyboard Interaction

**None.** Both are pointer-only.

For `jigDragScroll` that is usually fine: the host is a scroll container, so
give it `tabindex="0"` and the browser's own arrow-key, Page and Home/End
scrolling covers the keyboard case completely. Drag-to-scroll then becomes a
pure convenience on top of a fully keyboard-operable scroller.

For `jigDrag`, whatever you do with the gesture needs its own keyboard path —
resizing a pane, reordering a list, panning a canvas. Under
[WCAG 2.1.1 Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)
the _outcome_ must be reachable without a pointer, and under
[WCAG 2.5.7 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
it must also be reachable without a _drag_ — buttons, a numeric input, or arrow
keys on a focusable handle all qualify.

### Swallowed Clicks

After a real drag, the synthesized `click` is cancelled in the capture phase.
This affects **every descendant**, so a drag that ends over a button does not
activate it. That is deliberate and keeps panning safe, but it means you cannot
rely on `click` alone for something a user might reach mid-gesture — keyboard
activation (`keydown` on Enter/Space, or a real `<button>`) is unaffected.

### Focus

Neither directive moves focus. A drag over a scroll container leaves the
keyboard focus where it was, so the next Tab press continues from the same
place — the behaviour a screen-reader user expects.

### Touch and Reduced Motion

`touchmove` is prevented over the host while a gesture is possible, so the page
does not scroll behind the drag. Pair it with `touch-action: none` on the host.

There is no animation, so `prefers-reduced-motion` does not apply. If you add
momentum or easing on top of `dragged`, gate it on that media query.
