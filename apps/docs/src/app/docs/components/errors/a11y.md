`jigErrors` resolves messages; it renders nothing itself and sets no ARIA
attributes. The accessibility of a validated field is therefore split across
three parties, and you own the wiring between them.

## Keyboard

| Key | Action                                                            |
| --- | ----------------------------------------------------------------- |
| —   | No keyboard interaction. The directive only computes error state. |

## The three responsibilities

| Concern                          | Owned by                              |
| -------------------------------- | ------------------------------------- |
| The message text                 | `jigErrors`                           |
| `aria-invalid` and invalid style | the control (`invalid` + `invalidOn`) |
| Associating message with field   | **you** — via `aria-describedby`      |

## Associate the message with the field

Nothing wires `aria-describedby` automatically. Point the field at the hint's
`controlId` so the message is announced as the field's description rather than
as orphaned text:

```html
<jig-input-field [label]="'Email'">
  <input
    jigInput
    [formControl]="email"
    jigErrors
    [jigErrorsHint]="hint"
    [attr.aria-describedby]="hint.controlId()"
  />
</jig-input-field>
<jig-hint #hint />
```

## Announcing changes

`jig-hint` swaps message text in **without** a live region, so a message that
appears while focus is elsewhere is not announced. That is the right default
for `showOn="touched"` — the user has just left the field, and the message is
read the next time they reach it.

It is not sufficient when errors appear away from the field:

- **On submit** (`jigErrorsShowOn="submitted"`), announce the outcome yourself
  — an error summary in a live region, or move focus to the first invalid
  field. A silent form that simply refuses to submit is a common failure of
  [WCAG 3.3.1 Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html).
- **From the server** (`jigErrorsCustom`), the same applies: the response
  arrives long after the interaction that caused it.

## Do not rely on colour

The invalid border and the red hint carry the same information twice, but both
are colour. The message text is what satisfies
[WCAG 1.4.1 Use of Colour](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
and [3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)
— so do not set `jigErrorsShowOn="never"` on a control that still shows an
invalid border.

## Write messages that help

[WCAG 3.3.3 Error Suggestion](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)
asks for a correction, not just a diagnosis. Prefer "Enter a date as
DD.MM.YYYY" over "Invalid date". The default messages are deliberately generic
— override them per field with `jigErrorsMessages` where you can say something
specific.

Use `jigErrorsMode="all"` when several rules can fail at once; showing only the
first makes the user resubmit repeatedly to discover the rest.

## Timing

Showing errors while the user is still typing (`showOn="dirty"` on a field with
a length rule) is hostile to screen-reader users, who hear the field's
description change under them. `touched` is the accessible default; keep it
unless you have a reason.

## Pending state

While an async validator runs, the hint shows a translated "validating"
message regardless of `jigErrorsShowOn`, so the wait is perceivable instead of
looking like nothing happened.
