### Roles & Attributes

`awd-defer` has no role of its own. It sets `aria-hidden` on the host to match
its open state, so closed content is excluded from the accessibility tree.

## Keyboard

| Key | Action                                                       |
| --- | ------------------------------------------------------------ |
| —   | No keyboard interaction. It only controls whether UI exists. |

## `aria-hidden` and focusable content

While closed with `hiddenOnClosed` on, the host is _visually_ hidden
(`visibility: hidden`, moved off-screen) and marked `aria-hidden="true"`. It is
not removed.

`visibility: hidden` does take an element out of the tab order, so focusable
content inside is unreachable — but this is exactly the configuration that
produces the worst failure mode if it ever changes:
`aria-hidden="true"` on a subtree that contains a focusable element is an
[axe violation](https://dequeuniversity.com/rules/axe/4.10/aria-hidden-focus)
and traps screen-reader users on an element they cannot perceive.

The safe rule: **do not cache content that contains focusable elements.** With
the default `cache="false"` the subtree is destroyed on close and the question
does not arise.

## Announcing appearance

Content appearing is a change of context the user may not notice. `awd-defer`
announces nothing — if the content is a result of the user's action, either
move focus into it or announce it through a live region, exactly as you would
for any other conditionally rendered UI.

## Deferral and assistive technology

Deferred content does not exist before the first open, so it is not in the
accessibility tree, not searchable by a screen reader's find, and not reachable
by heading navigation. That is correct for genuinely hidden UI, but it means
`awd-defer` must never wrap content that should be discoverable — a section of
a page, a landmark, or anything referenced by `aria-describedby` /
`aria-controls` from outside.
