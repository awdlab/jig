Input field is a composition wrapper: it renders a `<label>` and associates it
with the projected input via a generated `id`/`for` pair. It adds no semantics of
its own to the input beyond labelling.

## Keyboard

| Key | Action                                                                        |
| --- | ----------------------------------------------------------------------------- |
| —   | No keys of its own; clicking the field forwards focus to the projected input. |

## ARIA & screen readers

The `<label>` is tied to the projected input through `for`/`id`, and
`aria-labelledby` is set on the input from the `labelledBy` input. The clear
button has a localized `aria-label`, and the host becomes `inert` when disabled.
The wrapper does **not** set `aria-invalid`/`aria-readonly`/`aria-disabled` — its
`invalid`/`readonly`/`disabled` inputs only toggle styling, and the theme reads
`aria-invalid`/`aria-readonly` that you set on the input itself.

## Owning the id

The field owns the projected input's `id`: it writes `inputId()` onto the
element, so an `id` you set on the `<input>` yourself is replaced by the field's
value. Set it on the field instead when an external `<label for>` (or
`aria-controls`/`aria-describedby`) has to reference it:

```html
<label for="login-username">Username</label>
<jig-input-field [inputId]="'login-username'">
  <input ngnInput autocomplete="username" />
</jig-input-field>
```

Without a literal id, read it back from the field via a template reference —
`[for]="usernameField.inputId()"` on `<jig-input-field #usernameField>`.

## Developer responsibilities

- Project the actual `input`/`textarea`.
- Provide a `label` (otherwise no `<label>` renders) or an external `labelledBy`.
- Set the input's `id` through the field's `inputId`, never on the projected
  `<input>`.
- Set `aria-invalid`/`aria-readonly` on your own input when those states should
  reach assistive tech — the wrapper only styles them.
