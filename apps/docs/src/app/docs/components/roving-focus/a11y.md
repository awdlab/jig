These directives exist for accessibility — they implement the keyboard model
that the [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
prescribe for composite widgets. They supply the **behaviour**; you supply the
**semantics**.

### Roles & Attributes

The directives set only what the focus model requires:

| Mode               | On the group                         | On the items                        |
| ------------------ | ------------------------------------ | ----------------------------------- |
| `tabindex`         | —                                    | `tabindex="0"` on active, `-1` rest |
| `activedescendant` | `aria-activedescendant`, `aria-owns` | generated `id`, no `tabindex`       |

Everything else is yours. A group is not a widget until you give it a role and
a name:

```html
<div ngnRovingGroup role="toolbar" aria-label="Text formatting">
  <button ngnRovingItem>…</button>
</div>
```

Pick the role pair that matches the widget — `toolbar` + `button`, `tablist` +
`tab`, `radiogroup` + `radio`, `listbox` + `option`, `menu` + `menuitem` — and
set `orientation` to match `aria-orientation` if you also declare that.

### Keyboard Interaction

| Key        | Action                                               |
| ---------- | ---------------------------------------------------- |
| Tab        | Moves into the group (one stop) and out again        |
| ← / →      | Previous / next item when `orientation="horizontal"` |
| ↑ / ↓      | Previous / next item when `orientation="vertical"`   |
| Home / End | First / last enabled item, in both orientations      |

Keys are consumed only when the group acts on them, so the unused arrow pair
still scrolls the page. Modified presses (Ctrl/Meta/Alt) are never intercepted.

### Focus Behaviour

The group deliberately does **not** focus anything on mount — it only assigns
the tab stop, so rendering a toolbar never yanks focus from where the user is.

`syncActiveIndex()` exists for the same reason: when your own code changes the
selection, the tab stop must follow, but focus must not jump. Using
`setActive()` there would move focus and violate
[WCAG 3.2.1 On Focus](https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html).

### Disabled Items

Disabled items are skipped by keyboard navigation and cannot be activated by
pointer, but they stay in the DOM and remain announced. Prefer `aria-disabled`
over the native `disabled` attribute if the item should still be discoverable
by a screen reader — and remember to set the item's `disabled` signal either
way, since the native attribute alone does not reach the group.

### Focus Visibility

Because the tab stop moves rather than the outline being drawn by the browser
on a container, every item needs a visible focus indicator of its own
([WCAG 2.4.7 Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)).
In `activedescendant` mode there is no DOM focus on the item at all — you must
style the active item yourself (bind to `isActive()`), and the group keeps the
real focus ring.

### Testing

Verify with the keyboard alone: Tab reaches the group once, arrows move inside
it, Home/End jump, Tab leaves — and a screen reader announces the item's role,
name, and position.
